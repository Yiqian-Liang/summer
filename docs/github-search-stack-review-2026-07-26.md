# 多平台原生搜索开源方案选型报告

日期：2026-07-26  
项目：Summer Research Platform  
结论依据：逐项阅读指定仓库及其关键下游仓库的源码、测试、许可证和登录/搜索实现；未使用项目宣传页代替源码判断。

## 一句话结论

**在本轮静态审查的候选中，现阶段最适合作为“用户侧、带本人登录态、Web 版原生搜索”基础的是 OpenCLI，而不是 Agent Reach 或 MediaCrawler。**

- OpenCLI 复用每个用户自己 Chrome 里的登录态，并调用平台的原生网页或 Web API，是候选中最接近“这个用户亲自在平台 Web 版搜索”的方案；本轮尚未用真实账号验证结果一致率。
- 它不是可直接部署到服务器的搜索 API。公开网页不能直接调用 OpenCLI 的本地 daemon；需要一个用户侧伴侣程序或专用浏览器扩展完成安全配对。
- MediaCrawler 的中国平台覆盖更完整、也更适合服务器集中爬取，但许可证明确限定学习研究、禁止大规模爬取；不能直接作为公开多人平台的生产后端。
- SearXNG 可作为免费的公共网页搜索兜底，但不能替代小红书、抖音、微博等平台内搜索。

因此，推荐的最小方案是：

1. 保留本项目现有 SQLite 索引和结果排序。
2. 增加可选的“登录平台实时搜索”，由用户电脑上的 OpenCLI 执行。
3. Cookie 永远留在用户电脑，只把规范化后的搜索结果交给 Summer 页面。
4. 暂不接入 Agent Reach、EasySpider、Crawl4AI。
5. MediaCrawler 只保留为本地研究/管理员试验工具，公开使用前先取得作者书面许可。
6. 只有确定要替换付费公共网页搜索时，再部署 SearXNG。

## 需求中必须先说清的边界

下面五项无法由一个免费开源项目同时无条件满足：

1. 平台方零 API 费用；
2. 用户无需安装、无需登录；
3. 覆盖所有平台；
4. 与每个用户在平台内看到的结果完全相同；
5. 可稳定支持公开、多用户、大规模运行。

原因不是代码量，而是搜索结果本身依赖用户账号、Cookie、地区、设备、风控、A/B 实验和个性化排序。没有用户登录态，只能得到公开网页索引或平台游客结果；把一个服务器账号共享给所有用户，又会遇到账号安全、并发、封禁和许可证限制。

本报告中的“原生结果”应理解为：

- **可以接近同一用户、同一时刻在平台 Web 版搜索看到的结果；**
- **不能承诺与手机 App 完全相同；**
- 平台页面变化、分页上限和风控仍可能造成差异。

“免费”也只能表示没有第三方搜索 API 调用费或商业许可证费，不代表服务器、带宽、验证码、代理和长期维护成本为零。

## 各项目源码结论

### 1. Agent Reach：是安装/路由层，不是搜索引擎

关键证据：

- `agent_reach/channels/xiaohongshu.py` 将小红书能力依次路由到 OpenCLI、xiaohongshu-mcp 或 xhs-cli。
- `agent_reach/integrations/mcp_server.py` 只暴露状态检查，并明确让 Agent 直接调用上游工具。

它的价值是帮助 AI Agent 检查“哪些外部 CLI 已安装”，而不是为 Summer 提供统一、稳定的搜索结果 API。接入它仍然要接入并维护下游工具，因此会多一层依赖但不减少本项目的工作。

**结论：不接入 Agent Reach，直接选它实际依赖的 OpenCLI。**

### 2. OpenCLI：最接近目标，但不是服务器 SaaS

关键证据：

- `clis/xiaohongshu/search.js` 打开小红书原生搜索页并从实际结果卡片提取数据。
- `clis/douyin/search.js` 打开抖音原生视频搜索页，并在未登录时明确报错。
- `clis/weibo/search.js` 使用 `s.weibo.com` 原生搜索。
- `clis/zhihu/search.js` 调用 `/api/v4/search_v3`。
- `clis/bilibili/search.js` 调用 B 站 WBI 搜索接口。
- `clis/twitter/search.js` 使用 X 的 SearchTimeline。
- `clis/linkedin/search.js` 使用用户会话下的 Voyager 接口。
- 仓库共有 94 个 `search.js` 适配器，包含 Google Scholar、搜狗微信入口、Discord 桌面端等当前项目关注来源，但后两者有上述范围限制。

登录与隐私模型：

- Chrome 扩展复用用户已经登录的平台会话；
- 扩展通过 `localhost:19825` 与本地 daemon 通信；
- `PRIVACY.md` 声明没有遥测，Cookie 只按目标域读取并留在本机；
- Apache-2.0 允许在满足许可证和 NOTICE 要求下修改、分发和商用。

Apache-2.0 只解决 OpenCLI 代码本身的使用许可，并不授予对目标平台进行自动化访问的权利。公开上线前仍需逐个平台核对服务条款、账号风控、隐私与数据合规要求。

重要接入限制：

- `src/daemon.ts` 故意拒绝普通网页 Origin；
- `/command` 要求 `X-OpenCLI` 头且不开放 CORS；
- 因此 Summer 网页不能直接 `fetch("http://localhost:19825")`；
- 这是正确的安全设计，不能为了省事直接关闭。

所以，本项目需要一个很薄的用户侧集成层：由受信任扩展在 Summer 页面和 OpenCLI 之间传递“用户明确发起的搜索命令”和结果。结果默认只在当前页面展示；若要上传服务器缓存，必须明确告知并征得用户同意、最小化字段。不要把 Cookie 传给 Summer 服务器，也不要把本地 daemon 暴露到公网。

**结论：它是最好的技术和许可证基础，但需要一次真实的浏览器端接入开发。**

### 3. xiaohongshu-cli：小红书能力不错，但不足以作为总方案

`xhs_cli/client_mixins.py` 的 `search_notes` 调用小红书 Web 搜索接口，支持关键词、分页、排序和类型过滤；`signing.py` 负责签名，Cookie 可来自本地浏览器或扫码登录。

优点：

- 返回结构化 JSON/YAML；
- 小红书搜索能力比通用网页抓取更专注；
- 有单元测试和需真实登录态的 smoke 测试。

问题：

- 只覆盖小红书；
- 版本仍标为 Alpha；
- `pyproject.toml` 和 README 声明 Apache-2.0，但仓库根目录没有 LICENSE 文件，公开产品使用前应要求作者补齐或书面澄清。

**结论：可参考接口设计，不作为本项目依赖。**

### 4. SearXNG：适合公共网页，不等于平台内搜索

SearXNG 是成熟的元搜索引擎，可聚合 Google、Bing、Baidu 等上游，也有默认关闭的 Bilibili 引擎，并能显式启用 JSON 输出；默认配置只开放 HTML。

它不能取得用户在小红书、抖音、微博等登录后看到的原生排序，只能找到被公共搜索引擎收录的页面。收录范围、更新时间和排序都会不同。

许可证为 AGPL-3.0。若修改 SearXNG 并通过网络提供服务，需要向该服务的远程用户提供相应修改版本的源代码。把未修改的 SearXNG 作为独立服务、仅经 HTTP 调用，不当然要求整个 Summer 项目开源；具体组合和部署方式仍应单独确认。

**结论：未来用于替换 SerpApi 的普通网页搜索部分；不要把它宣传成平台原生搜索。**

### 5. EasySpider：通用，但意味着自己维护所有网站

EasySpider 通过 Electron、Selenium 和可视化任务编排实现通用浏览器爬取。理论上每个平台都能录制流程，实际仓库没有本项目所需的一组可直接使用、统一输出的搜索适配器。

每个平台都要自己维护登录、选择器、滚动、分页、风控和结果归一化。项目体积和运行栈明显重于当前需要，AGPL 也增加公开服务的合规工作。

**结论：不是“现成多平台搜索”，不选。**

### 6. Crawl4AI：用途不匹配

Crawl4AI 的核心是已知 URL 的抓取和内容提取。仓库中的 Google Search crawler 也不是多平台原生搜索层，而且其固定参数和可选 LLM schema 生成不适合本项目的免费、稳定目标。

**结论：后续若需要提取某条已知结果页正文可再考虑；当前搜索功能不需要它。**

### 7. MediaCrawler：集中式技术最强，许可证是硬阻塞

当前项目内的 MediaCrawler 已有小红书、抖音、快手、B站、微博、贴吧、知乎原生搜索实现，是“中国平台服务器集中搜索”方向上最完整的候选。

但其 `LICENSE` 明确写明：

- 仅限学习和研究；
- 不得用于大规模爬虫；
- 未经书面同意不得商业使用。

平台是否收费并不能自动规避“大规模爬虫”限制。免费开放给很多用户仍可能超出授权范围。

**结论：没有作者书面许可，不把它放进公开多人生产链路。**

## 与当前 Summer 项目的差距

当前真实搜索链路是：

1. `/search` 先查本地 SQLite FTS；
2. 配置密钥后再调用 Gemini Grounding 或 SerpApi；
3. 微信使用免费的搜狗索引；
4. MediaCrawler 是独立运行、导出后导入 SQLite 的管理员流程，不会随每次用户搜索实时运行。

当前数据库里 `provider=mediacrawler` 的记录仍为 0，`MediaCrawler/data` 也不存在，因此现阶段页面上没有任何真实的 MediaCrawler 导入结果。

此前提到的“移动目录后 runner 找错位置”在当前代码中已经处理：

- `app/mediacrawler_runner.py` 会先找项目内 `./MediaCrawler`；
- 找不到时才回退到项目外 `../MediaCrawler`。
- 实测 `python3 -m app.mediacrawler_runner --dry-run` 当前会定位到项目内目录，并因 `MediaCrawler/data` 不存在而以非零状态明确报错，不再返回“0 文件、0 错误”的成功假象。

仍存在的功能缺口：

- runner 默认只跑 `xhs, zhihu, bili, wb, tieba`；
- importer 也只实现这五类；
- MediaCrawler 本身支持的 `dy` 和 `ks` 尚未接入本项目；
- 但鉴于许可证阻塞，现在不值得先扩这两类生产接入。

## 推荐架构

```text
用户在 Summer 发起搜索
        |
        +-- 本项目 SQLite 缓存/历史结果
        |
        +-- 用户选择“登录平台实时搜索”
                |
                v
        Summer 专用受信任扩展
                |
                v
        用户本机 OpenCLI + Chrome 登录态
                |
                v
        平台原生网页/API
                |
                v
        默认只在当前页面展示规范化结果，不返回 Cookie
        （用户明确同意时才上传服务器缓存）
```

建议统一返回现有项目已经使用的最小字段：

`title, url, description, source, provider, author, published_at, query`

不要一开始做账号托管、任务队列、代理池或跨用户 Cookie 存储。用户侧搜索天然完成账号隔离，也把平台风控限制在发起搜索的本人会话中。

## 最小实施顺序

### 第一步：只打通小红书

目标不是一次接完所有平台，而是验证整条安全链路：

1. Summer 页面检测专用扩展是否安装；
2. 用户点击“用我的登录态搜索”；
3. 扩展触发本地 OpenCLI 小红书搜索；
4. 结果映射为现有搜索结果结构并显示；
5. 验证 Cookie 没有进入服务器日志、请求或数据库，结果也不会在未同意时上传。

### 第二步：复用同一通道增加现有来源

按当前页面价值依次增加：

1. 知乎、B站、微博、贴吧；
2. LinkedIn、X/Twitter；
3. 微信、Scholar、Discord。

这些都已有 OpenCLI 搜索适配器，不应为每个平台另建一套服务。

### 第三步：再决定两个可选项

- 如果公共网页搜索 API 成本成为问题，再自建 SearXNG。
- 如果快手成为明确需求，再独立写一个 OpenCLI 快手适配器。

## 验证限制

本轮完成了静态源码、许可证、测试布局和调用路径审计，但没有用户的平台登录态，因此没有执行“小红书同一关键词：平台网页 vs 工具返回”的真实账号对照测试。任何项目都不能仅凭 README 证明结果完全一致。

Agent Reach 的本地测试尝试在收集阶段因当前环境缺少 `rich` 依赖而停止，这不是项目测试失败，也不影响“它是路由层而非搜索实现”的源码结论。

正式接入前必须做一轮小规模验收：

- 同一用户、同一浏览器、同一关键词；
- 对比平台 Web 搜索前 20 条与 OpenCLI 前 20 条；
- 记录顺序一致率、漏项、字段完整率和登录失效行为；
- 至少覆盖小红书、知乎、B站各一次。

## 最终选择

**在上述限定下，选 OpenCLI，直接接，不经过 Agent Reach。**

这是唯一同时具备以下特征的候选：

- 许可证清楚、允许产品化；
- 能复用每个用户自己的登录态；
- 已覆盖当前 Summer 绝大多数来源；
- 搜索来自平台原生网页/API，而不是公共搜索引擎的 `site:` 结果；
- Cookie 可以留在用户本机。

要接受的代价是：用户第一次需要安装浏览器扩展和 OpenCLI 本地组件，并在各平台登录。若坚持“用户零安装、平台全自动、所有平台原生结果、运营方零成本”，本轮候选中没有可行方案。
